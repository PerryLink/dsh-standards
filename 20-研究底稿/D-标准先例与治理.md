## 0. 五句话结论

1. **GB / GB/T / GB/Z 三者的真实差别是"法律效力来源"，不是"技术等级高低"**。GB 由国务院批准发布、必须执行；GB/T 由国务院标准化行政主管部门制定、鼓励采用；GB/Z 是"技术尚在发展中、尚不具备制定国家标准条件"时的引导性文件，**不具有强制性**（《国家标准化指导性技术文件管理规定》第九条）。把 DSH 三级标准类比成"及格 / 良好 / 优秀"或 "Basic / Recommended / Advanced" 是对 GB/Z 的**系统性误读**。
2. **GB/Z 的适用条件与 DSH 现状高度同构**——两者都是"宿主仍在快速演进、技术尚在发展中"。GB/Z 那套"登记制立项 + 1/2 赞成即通过 + 12 个月研制上限 + 复审周期最长不超过三年 + 复审结论可以是废止 / 继续有效 / 升为推荐性国标"的机制，是**比名字更值得借的东西**。
3. **可类比生态里，真正有效的分级都不是"质量打分"，而是"可判定的准入 + 权限分级 + 事后执行"**。Koishi（Cordis 母生态）的市场准入只校验 `package.json` 的 5 个字段，不评质量；Android 用 normal/dangerous/signature 做**权限**分级而非质量分级；Chrome 用权限声明 + 周期性复审。
4. **DSH 生态已有的 7 类评级尝试，覆盖了"检测 / 打分 / 证据 / 准入 / 格式 / 退出"六块积木，但没有一块能承载"标准符合性"**——缺的是：被生态承认的发布主体、公开的"检查结果 → 等级"映射规则、以及强制执行的落点。
5. **不建议直接借用 GB / GB-T / GB-Z 命名**。推荐 **DS-C / DS-R / DS-G（Core / Recommended / Guidance）**：结构三分法照抄，代号一个字不借。理由见 §5。

# 一、中国国家标准体系的准确语义

## 1.1 法律框架（四层）

| 层级 | 文件 | 关键条款 |
|---|---|---|
| 法律 | 《中华人民共和国标准化法》（1988 通过，2017-11-04 修订，2018-01-01 施行） | 第二条（分类）、第十条（强制性国标）、第十一条（推荐性国标）、第二十一条（推荐性不得低于强制性）、第二十四条（编号规则）、第二十五条、第二十九条（复审周期）、第三十六/三十七条（法律责任）、第三十九/四十二条（编号违规处理） |
| 部门规章 | 《国家标准管理办法》（国家市场监督管理总局） | 第十七条（GB/Z 的制定条件）、第三十二条（代号）、第三十六条（实施效力） |
| 规范性文件 | 《国家标准化指导性技术文件管理规定》（2025-03-31 修订通过，2025-04-07 公告施行，同时废止 1998 年旧规定） | 第二条（定义）、第三条（规范类/报告类）、第八条（无中央财政补助）、第九条（不具强制性）、第二十三条（编号）、第二十四条（封面）、第二十六条（复审） |
| 官方答复 | 市场监管总局标准技术管理司公众留言答复（2026-01-12），关于"GB/Z 是否属于正式的国家标准文件" | 明确三者的三重区别：技术内容 / 制定程序 / 实施效力 |

## 1.2 三者对照

| 维度 | **GB** 强制性国家标准 | **GB/T** 推荐性国家标准 | **GB/Z** 国家标准化指导性技术文件 |
|---|---|---|---|
| **法律定位** | 国家标准，**必须执行** | 国家标准，**鼓励采用** | 国家标准的**重要补充**，供参考使用 |
| **适用条件**（法条原文） | 标准化法第十条：对保障**人身健康和生命财产安全、国家安全、生态环境安全以及满足经济社会管理基本需要**的技术要求，*应当*制定 | 标准化法第十一条：对满足**基础通用、与强制性国家标准配套、对各有关行业起引领作用**等需要的技术要求，*可以*制定 | 《国家标准管理办法》第十七条 + 《管理规定》第二条：**技术尚在发展中，需要引导其发展或者具有标准化价值的项目**；相关科研成果**尚不具备制定国家标准条件**时 |
| **提出/起草** | 国务院有关行政主管部门依职责提出、组织起草、征求意见、技术审查 | 由国务院标准化行政主管部门制定；应组织由相关方组成的标准化技术委员会承担起草与技术审查 | 任何单位和公民均可向技术委员会或国务院标准化行政主管部门提出项目建议 |
| **批准发布** | **国务院批准发布或者授权批准发布** | 国务院标准化行政主管部门**统一批准、编号**，以公告形式发布 | 国务院标准化行政主管部门批准、编号，以公告形式发布 |
| **立项** | 国务院标准化行政主管部门**立项审查**，符合第十条才予以立项 | 正常立项程序 | **登记制**——技术委员会评估通过后登记项目信息即可组织起草，**不再进行立项审批** |
| **技术审查门槛** | 严格 | 三分之二以上赞成 | 参加投票委员不少于 3/4，**参加投票委员 1/2 以上赞成即为通过**（由 2/3 下调） |

| **强制力** | **必须执行**。不符合强制性标准的产品、服务，**不得生产、销售、进口或者提供**（标准化法第二十五条；《国家标准管理办法》第三十六条） | **鼓励采用**。在基础设施建设、基本公共服务、社会治理、政府采购等活动中鼓励实施 | **不具有强制性**，不通过引用获得强制效力，仅供有关各方**参考使用** |

| **复审** | 复审周期一般不超过 5 年 | 复审周期一般不超过 5 年 | **规范类：复审周期最长不超过 3 年**；结论为 ①废止 ②继续有效（继续使用期限一般不超过 3 年）③**制定为推荐性国家标准**。报告类：视情况复审，结论为废止/修订/继续有效 |
| **财政** | 有 | 有 | **制修订工作不予安排中央财政补助经费**（管理规定第八条） |
| **版权** | — | — | 依法受版权保护，**批准发布主体享有其版权**（管理规定第五条） |

## 1.3 编号规则

《国家标准管理办法》第三十二条原文：

> 国家标准的代号由大写汉语拼音字母构成。强制性国家标准的代号为"GB"，推荐性国家标准的代号为"GB/T"，国家标准样品的代号为"GSB"。指导性技术文件的代号为"GB/Z"。国家标准的编号由国家标准的代号、国家标准发布的顺序号和国家标准发布的年份号构成。

- 格式：`GB XXXXX-XXXX` / `GB/T XXXXX-XXXX` / `GB/Z XXXXX-XXXX`（代号 + 顺序号 + 发布年号）
- **GB/Z 顺序号单独编号**（《管理规定》第二十三条），不与 GB、GB/T 共用序列——这是"它是独立一类文件、不是 GB 的子级"的编码层证据。
- **GB/Z 封面标注发布日期，不标注实施日期**（《管理规定》第二十四条）——因为它没有"强制执行起始点"。
- 编号规则的制定权：标准化法第二十四条"标准的编号规则由国务院标准化行政主管部门制定并公布"。

## 1.4 GB/Z 的"技术尚在发展中"特性——本报告最关键的一条语义

市场监管总局标准技术管理司 2026-01-12 答复给出的三重区别，逐字摘录：

> **在技术内容方面**：国家标准一般是**成熟的技术或实践经验的总结**，是需要在全国范围内统一的技术要求。指导性技术文件是针对**发展过程中的新技术**，在**尚不具备制定国家标准条件**时，为引导其进一步探索创新发展而制定的一种标准化文件。
> **在制定程序方面**：与国家标准制定程序比较，指导性技术文件制定程序**更加简洁、灵活、高效**……以便快速启动研制工作……有效增加技术文件供给数量。
> **在实施效力方面**：强制性国家标准必须执行，代号是 GB。推荐性国家标准鼓励采用，代号是 GB/T。国家标准化指导性技术文件**不具备强制实施的法律效力**，供有关各方参考使用，代号为 GB/Z。

《管理规定》第三条进一步把 GB/Z 拆成两类，这个二分法对 DSH 极有参考意义：

- **规范类**：旨在为技术尚在发展中的标准化对象提供规则、指南或特性，**未来有可能转化为国家标准**。适用情形：(一) 具有一定应用前景但技术尚处于发展过程中或变化较快的新技术、新产业、新业态或新模式；(二) 采用国际标准组织的技术规范/可公开提供规范。
- **报告类**：旨在提供与标准化对象有关的数据、经验总结、发展趋势、检测报告等**资料性信息**。适用情形：(一) 具有推广或示范价值的标准化工作经验或做法；(二) 国标制定、实施过程中具有传播价值的信息；(三) 采用国际国外组织的技术报告。

**语义要点（防止误用）**：

> GB/Z **不是**"更高级的标准"，而是"**更不成熟、因而更快、更短命、更允许作废**"的标准。它的级别低不是因为它浅，而是因为它**尚未凝固**。
> 因此：把第三级命名为 "Advanced / 高级 / 进阶" 是**语义反转**，会诱导插件作者为了拿"高级"标签去追 Cordis 的未稳定 API——这恰恰是 GB/Z 制度设计要防止的行为。正确的措辞是 **Guidance / 指导 / 探索 / Frontier**。

## 1.5 "强制 / 推荐 / 指导"在执行力上的真实差别

| | 谁在强制 | 强制的落点 | 不遵守的后果 | 关键限定 |
|---|---|---|---|---|
| **GB** | 国家。法条自力执行 + 行政执法 | 产品/服务本身。标准化法第二十五条：**不得生产、销售、进口或者提供** | 民事责任（第三十六条）；依《产品质量法》《进出口商品检验法》《消费者权益保护法》查处，**记入信用记录并公示**；构成犯罪的追刑责（第三十七条） | 只有"保障人身健康和生命财产安全、国家安全、生态环境安全、满足经济社会管理基本需要"才能立项为强制。这是一个**极窄的口子**，且有立项审查把关 |
| **GB/T** | 无人强制，靠市场与采购引导 | 自愿采用 | 无直接法律后果 | **但有两个"变强制"的通道**：① 一旦被各方商定同意纳入经济合同，即成为各方必须共同遵守的技术依据，具有法律上的约束性；② 一旦企业自我声明公开执行该标准（标准化法第二十七条），企业生产的产品、提供的服务**应当符合其公开标准的技术要求**，此时第三十六条的民事责任就可以够到它 |
| **GB/Z** | 无人强制 | 参考 | 无 | 明确"不通过引用获得强制效力"（即：强制性标准引用了某个 GB/Z，也不会使该 GB/Z 变强制）；无中央财政补助；有版权 |

**这一层对 DSH 的直接推论**：

- DSH 生态里**唯一具备"GB 级强制力"的执行者，是宿主运行时本身**（Cordis 的加载契约、CLI 的安装校验）。任何社区组织、任何市场、任何评分工具，其"强制"最多只能做到 GB/T 的层次——即"鼓励采用 + 一旦被下游（市场/企业 policy）声明采用就在该范围内产生约束力"。
- 因此 DSH 三级标准的**第一级如果自称"强制"**，它的强制力来源只能是"写进 CLI / 宿主校验"，而不是"标准文本自己声明强制"。**否则就是空的**：一个没有执行落点的强制级，等价于一个徽章。
- GB/T 的两个"变强制通道"可以直接移植：**① 下游市场声明"本市场只收录达到 X 级的插件"；② 插件 README 自述"本插件符合 DS-C"，则该声明成为可核验的公开承诺**（对应标准化法第二十七条的自我声明公开 + 第三十六条的责任）。

## 1.6 三级语义 → DSH 的映射（草稿，供 A/B/C 交叉校验）

| 国标层 | 国标语义内核 | DSH 对应内核 | 判定主体 | 执行落点 |
|---|---|---|---|---|
| **GB** | 底线安全 + 基本可用，必须执行 | 装得上、起得来、不破坏宿主、权限面可声明 | 机器（doctor 类工具） | CLI 安装校验 / 宿主加载校验 / 市场的收录前置门禁 |
| **GB/T** | 基础通用、起引领作用，鼓励采用 | 与 Cordis 契约正确对齐：生命周期、服务依赖声明、配置 schema、卸载干净 | 机器为主 + 生态工作组共识 | 市场默认筛选、企业 policy、README 自我声明 |
| **GB/Z** | 技术尚在发展中，引导探索，参考使用，短周期复审，成熟后升为推荐级 | 充分利用 Cordis 特性（高阶 pattern、性能/吞吐、组合式能力） | 个人或小团队署名，**登记制**，1/2 共识即可 | 无强制；附最佳实践案例；**3 个月复审**，可废止可升为 DS-R |

| **Apple App Store** | 五章指南：Safety / Performance / Business / Design / Legal；4.3 反垃圾（相同二进制、功能极简）、5.1 隐私、3.1.1 强制 IAP | Apple 人工 + 自动；约 90% 在 24h 内审完；申诉走 Resolution Center / App Review Board | 平台**强制**，且是**唯一分发渠道** → 强制力最强 | **准入 + 内容审查**，争议最大 |
| **Homebrew (core/cask)** | 知名度（GitHub ≥30 forks / 30 watchers / 75 stars；自荐需 90/90/225）、活跃维护、无未修补漏洞、可工作 livecheck、可验证上游分发、Gatekeeper 通过、许可证（core 须 DFSG 兼容） | Homebrew 维护者人工评审 PR | **强制**（不符则拒绝），但**明确"符合不保证接受，缺一条也不必然拒绝"** | **准入 + 维护者自由裁量** |
| **Debian main/contrib/non-free** | **许可证与依赖自洽性**：main = DFSG 合规且不依赖区外软件（唯一被视为"Debian 发行版"的部分）；contrib = 自身 DFSG 合规但依赖区外；non-free = 不合规 DFSG | Debian Policy + ftp-master 审核 | **强制**（分区是硬性归档规则） | **许可/依赖分区**，非质量分区 |
| **Ubuntu supported / universe** | 支持承诺：main/restricted 由 Canonical 官方安全更新；universe/multiverse 由社区维护 | Canonical vs 社区 | **事实上的自律分工** | **维护承诺分级** |

## 2.2 逐项展开（维度 / 执行者 / 强制自律 / 失败案例与教训）

### 2.2.1 Koishi 插件市场 —— **参考价值最高**（Cordis 的母生态）

**分级维度**：只有一条——**能否被市场索引**。条件完全写在 `package.json` 上：
- `name` 必须是 `koishi-plugin-*` / `@bar/koishi-plugin-*` / `@koishijs/plugin-*`（官方保留）
- `version` 符合 semver
- `peerDependencies` 必须包含 `koishi`（**同步版本依赖**，例：`"koishi": "^4.3.2"`）
- 不得声明 `private: true`；最新版本不得被弃用
- 可选 `koishi` 字段：多语言 `description`、`service.{required,optional,implements}`（**服务依赖声明**）、`locales`、`preview`（标记"开发中"）、`hidden`（不显示）

**谁执行**：市场索引自动校验。npm 发布 → registry.koishi.chat 轮询（约 15 分钟）→ 校验 → 入库。**没有人工审核环节**。

**强制还是自律**：事实上的自动门禁——不满足就不出现在市场里，但**插件依然可用**（Koishi 仍可手动安装）。所以是"**名录强制、安装不强制**"。

**教训 / 可借鉴**：
- ✅ **Koishi 作为 Cordis 母生态，选择的路径是"只校验可被机器判定的元数据，一个主观判断都不做"**。这与 B 路（Cordis 契约可判定性矩阵）的结论应当是一致的：`peerDependencies` + `service.required/implements` 就是这个生态里**天然存在、无需发明**的契约声明位。DSH 三级标准的第一级，**最省力的形态就是 Koishi 模式的 DSH 版**。
- ✅ `preview` 和 `hidden` 两个布尔位是**"尚未达标但允许存在"的过渡态**——对应 GB/Z 的"发展中"，也对应 PerryLink 的 🧊FROZEN。三级体系需要一个等价位。
- ⚠️ Koishi 模式**完全不覆盖质量、安全、维护活跃度**。它的代价是市场里长期存在大量"能装上但没人维护"的插件。这解释了为什么 DSH 生态会自发长出 dsh-score / dsh-market 这些打分工具——**打分是准入制缺位后的生态自救**。三级标准要接手的正是这块。

### 2.2.2 VS Code 扩展市场

**维度**：manifest 结构（`name`/`version`/`publisher`/`engines.vscode` 四项必填，`engines.vscode` 不能是 `*`）、图标 128×128、README/CHANGELOG/LICENSE 齐备、`.vscodeignore` 排除源码与 devDeps、`categories` 白名单、`pricing`、`capabilities.untrustedWorkspaces`。

**谁执行**：`vsce` 在打包与上传期做机械校验；Marketplace **不做人工代码评审**。

**强制/自律**：平台强制（不符则拒收），但**只到格式层**。

**失败案例与教训**：
- ❌ **"格式合规"被普遍误读为"安全/质量合格"**。实际上传后无任何代码审查，恶意扩展靠"快照合规"上架、靠后续更新换芯。这个失效模式与 Chrome 完全相同（见下）。
- ❌ 同名同版本不可重发、publisher 命名空间在两个 registry（Marketplace / Open VSX）是**两套独立身份系统**，导致抢注与身份分裂——**命名空间必须由单一权威根锚定**（MCP Registry 用反向 DNS 解决了这一点）。

### 2.2.3 Chrome Web Store —— **"快照 vs 慢变量"的经典失效**

**维度**：开发者计划政策合规；**权限声明的最小必要性**（`<all_urls>` / `*://*/*` 这类宽泛 host 权限、tabs / downloads / cookies / webRequest 等敏感执行权限会被逐个核对"是否真的必要且被恰当使用"）；禁止代码混淆（minify 允许）；MV3 合规；禁止运行时拉取并执行远程代码；处理个人数据需隐私政策；功能与商店描述一致。

**谁执行**：自动扫描（恶意签名、混淆、危险 API 模式）+ 人工评审。深度评审触发信号：新开发者、新扩展、危险权限请求、显著代码变更。**发布后周期性复审**，触发源包括定期复审、新提交违规、用户举报。

**强制/自律**：平台强制。五种结果：通过 / 拒绝（邮件告知，列表不变，**不通知最终用户**）/ 警告（7–30 天整改）/ 下架 / 账号封禁。恶意软件可**不通知开发者直接下架**。

**失败案例与教训（本轮调研中最有价值的一条）**：
- ❌ **2026 年曝光的 108 个 Chrome 扩展 → 1 个 C2 → 5 个马甲身份**的工业化供应链攻击。攻击者把 108 个货位摊在 4 条品类线上，赌的是"商店审核的通过率 × 长尾搜索的命中率"，单个被下架、剩下的仍在——**打地鼠的疲惫留给防守方**。
- ❌ **根本失效点，原文说得很准**："审核是**快照**，攻击者交的是**慢变量**，今天守规矩的版本，明天一次更新就能换芯。"上架当下行为挑不出毛病、静态躺在包里没激活的代码不产生行为——**任何"某一时刻的审核结论"都无法对抗"后续的版本漂移"**。
- ✅ 可借鉴的三条：① **权限分级触发差异化审查强度**（宽权限 → 深审），这正是 Android 权限分级的商店版；② **周期性复审 + 用户举报触发**；③ **明确对外声明"审核 ≠ 安全背书"**。
- ❌ 反面：**拒绝时不通知最终用户**——审核结论的不透明使风险信号无法传导给使用者。

### 2.2.4 MCP Registry

**维度**：**只做元数据**。`server.json` 含：反向 DNS 唯一名（`io.github.user/server` 或 `com.yourdomain/server`）、描述、packages/remotes 位置、运行提示（args/env）、版本。**命名空间身份认证**（GitHub 账户所有权 / DNS 或 HTTP challenge）是唯一信任机制。

**谁执行**：registry working group（Anthropic、GitHub、PulseMCP、Microsoft 等）；社区可提交 issue 举报违规（spam / 恶意代码 / 冒充），维护者 denylist。

**强制/自律**：**自律**。官方明确：**不做代码安全扫描**，扫描委托给包注册中心与下游聚合器；仍在 preview，不提供数据持久性保证。

**教训**：
- ✅ **"元注册中心"分层是极重要的架构决策**：官方 registry 只做无观点的元数据 + 身份锚定，**分级、评分、策展全部下放给下游子注册中心**。这直接给出 DSH 三级标准的正确位置：**标准条款应当是中立的可复用规范，等级徽章由各个市场各自发放**。一个组织既写标准又发徽章又运营市场，就会变成 Apple。
- ✅ 反向 DNS 命名空间 = **身份锚**。DSH 生态当前靠 GitHub topic 自报，没有身份锚（`dsh-plugin-catalog` 也没有），这是 A 路"噪音大"的根因之一。
- ❌ 明确"namespace 认证 ≠ 代码验证"——**身份认证只解决冒充，不解决恶意**。

### 2.2.5 npm（provenance / score / audit）

**维度**：
- `npm publish --provenance`：基于 Sigstore（Fulcio 短证书 + Rekor 透明日志），证明"这个 tarball 由这个 CI 从这个源构建"，解决的是**来源真实性**，不是**质量**。
- `npm audit`：已知漏洞匹配。
- OpenSSF Scorecard：18 项检查，0–10 分，涵盖 branch protection、dependency pinning、SAST、fuzzing、signed releases、dangerous workflow、maintained 等。

**谁执行**：机器；Scorecard 由 OpenSSF（Linux 基金会）治理，每周扫 100 万+ 仓库。

**强制/自律**：自律 + 下游采用。

**失败案例与教训**：
- ❌ **刷分与失真（这是"评分即排名"最硬的实证）**：Zahan 等（ICSE-SEIP 2023）对 2,422 个 npm/PyPI 包的研究发现，**安全实践总分与已报告漏洞数之间存在反直觉的正相关**——高分并不等于漏洞更少。Scorecard 官方也自陈："The checks themselves are heuristics; there are false positives and false negatives."
- ❌ **评分覆盖不到真实攻击面**：polyfill.io 域名易主投毒（CDN 层）、tj-actions/changed-files 篡改 git tag（CI 层）、xz-utils 把恶意代码藏在构建脚本与测试产物里（专治静态与 repo 层审查）——**这三类攻击发生时，没有任何包健康分发生变化**。
- ❌ **评分的是源仓库，不是发布的 tarball**，二者可以背离。
- ✅ 可借鉴：**provenance 的思路（"证明产物来自声明的源"）> score 的思路（"给个分"）**。DSH 三级标准应优先采用可验证来源 + 可判定条款，而非加权总分。

### 2.2.6 Android 权限分级 —— **"分级什么"的范式纠正**

**维度**（官方定义）：
- **normal（一般权限）**：超出应用沙箱但风险很小，如 `SET_WALLPAPER`。系统在安装时**自动授予**，不提示用户。
- **dangerous（运行时/危险权限）**：访问用户私密数据或取得设备控制权，如 `READ_CALENDAR`、位置、联系人、麦克风、摄像头。必须在**运行时弹窗请求**，且不得假定已授予、每次访问前都要检查。
- **signature（签名权限）**：仅当请求方与**定义该权限的应用或 OS 使用相同证书签名**时才授予。用于特权服务（自动填充、VPN）或同一开发者的多应用互操作。**部分 signature 权限不适合第三方应用**。
- **appop（特殊权限）**：只有平台和 OEM 可定义（如在其他应用之上绘制）。

**谁执行**：Android 框架在运行时执行；一致性由 **CTS（兼容性测试套件）** 保证（"在搭载 Android 6.0 及更高版本的所有设备上，运行时权限模式必须保持一致。此一致性可通过 Android 兼容性测试套件 (CTS) 测试来保证"）。

**强制/自律**：**框架级强制**。

**教训**：
- ✅ **这是本报告中最重要的范式纠正**：Android 分级的不是"应用质量"，而是"**能力的风险等级 + 授予方式**"。normal/dangerous/signature 三档分别对应"自动授予 / 用户显式授予 / 同签名才授予"。
- ✅ **完美映射到 DSH 三级标准的真正设计变量**：一个插件声明"我要读全库文件"、"我要发起外网请求"、"我要注入 system prompt"，这些**权限面**（C 路的产出）才是应该被分级的东西，而"代码写得好不好"不是。
- ✅ `signature` 档给了一个精巧答案：**有些能力不按风险分级，而按"身份关系"分级**——只有宿主自己 / 官方组织签发的插件才能用。DSH 完全可以有对应档位（如"只有 `deepseek-ai/*` 命名空间可用"）。
- ❌ 已知滥用：组件导出后未做权限校验会被恶意应用代理特权（Oversecured 类漏洞）；自定义权限声明不当同样产生风险。→ **声明了权限不等于正确地实施了权限检查**，标准必须同时校验声明与实施。

### 2.2.7 Apple App Store —— **强制力最强，副作用也最强**

**维度**：五章指南（Safety / Performance / Business / Design / Legal）。4.3 反垃圾（相同二进制、功能极简）；5.1 隐私（相机/麦克风/HealthKit 需同意）；3.1.1 数字内容强制走 IAP。约 90% 在 24 小时内审完，首次提交驳回率约 35%（多为信息不全或崩溃）。

**谁执行**：Apple 人工 + 自动；申诉走 Resolution Center，可升级至 App Review Board。

**强制/自律**：平台强制，且是 iOS 唯一分发渠道 → **强制力天花板**。

**失败案例与教训（治理反面教材）**：
- ❌ **评审者成为瓶颈与权力中心**：开发者普遍报告"同一功能这次过、下次拒"，1 万+ 词的宽泛指南给了单个评审者巨大自由裁量权；申诉机制缺乏透明度与独立仲裁。
- ❌ **裁判与选手同体**：Apple 既是唯一分发渠道，又是唯一评审者、上诉法院和规则制定者。开发者的Screen Time / 邮件 / 家长控制类应用在与 Apple 自有功能竞争后被限制，此模式已被 EU、US DOJ、日本公正取引委员会援引为反垄断证据。英国 CMA 的 SMS 调查（2025）明确列出六类担忧，第一条就是"**app review 冗长且不可预测**，对创新应用尤甚"，并指出 Apple 在评审竞品应用时可接触竞争对手的商业敏感数据。
- ❌ **标准僵化的另一面**：指南频繁变更但解释权单方所有，开发者无法预判。
- ✅ 唯一可借鉴：**分层申诉**（Resolution Center → App Review Board）。DSH 三级标准必须内置**对称的上诉通道**（否则就是 Apple 的缩小版）。

### 2.2.8 Homebrew / cask —— **"门槛 vs 长尾"的正面样本**

**维度**（`Package-Acceptance-Policy`）：
- **知名度门槛**：GitHub ≥ 30 forks / 30 watchers / 75 stars；**自荐**（提交者邮箱在项目域名下）提高到 90 / 90 / 225；仓库 < 30 天通常不合格
- 上游公开存在 + 主页 + **活跃维护** + 无已知未修补漏洞 + **可工作的 livecheck**
- 不接收"用 Homebrew 补丁弥补上游停摆"的软件
- **core 必须开源且 DFSG 兼容**、可从源码构建、不得依赖 cask
- **cask** 必须用开发者自己发布或公开背书的下载源；通过 Gatekeeper；不得要求关闭 SIP
- **项目风险**：可因法律/基础设施/安全/项目连续性风险拒绝或移除
- **维护者自由裁量**：原文——"Meeting the documented criteria does not guarantee acceptance and missing one criterion does not require rejection in every case."；"New submissions may be held to a higher standard than existing packages"

**谁执行**：Homebrew 维护者人工评审 PR。

**强制/自律**：官方 tap 强制；但**不合格软件可进第三方 tap**——Homebrew 明确"通过第三方 tap 分发不代表 Homebrew 背书或支持"。

**教训**：
- ✅ **"不合格的东西有地方去"是门槛能维持的前提**。这条直接可用于 DSH：三级标准若配"未达标者进第三方目录"，门槛就可以硬；若只有一个市场，门槛必须软。
- ❌ **知名度门槛会直接砍掉长尾**。30 forks / 75 stars 放在 DSH 生态：**6–10★ 区间有 590 条**（dsh-market 目录快照），>5★ 约 2,686 个仓库——Homebrew 的门槛会把这批几乎全数排除。DSH 生态的长尾恰恰是当前活跃区（大量 6–10★ 单功能插件）。**第一级绝不能设知名度门槛**。
- ✅ **"新提交比存量要求更高"** —— 承认标准的棘轮效应，防止存量绑架标准。
- ✅ **不安全性声明**："Homebrew does not certify that every application distributed by a cask is safe"，恶意指控需**逐案评估**（安全产品有假阳性），移除需**精确定位文件+版本+校验和+多来源证据**，VirusTotal 单独不足为凭。→ **下架决策的证据标准**，值得照抄。

### 2.2.9 Debian main/contrib/non-free（+ Ubuntu universe）

**维度**（Debian Policy 2.2.2，原文）：
- **main**：唯一被视为"Debian 发行版"的部分。每个包必须 DFSG 合规；且**不得依赖 main 之外的包**来编译或运行（不得对非 main 包声明 Pre-Depends/Depends/Recommends/Build-Depends*，除非仅作为非默认备选）；不得 buggy 到"我们拒绝支持"；须满足全部 policy 要求。
- **contrib**：自身 DFSG 合规，但**构建或运行需要发行版之外的软件**（如依赖 non-free、或为非自由程序的 wrapper）。
- **non-free**：不符合 DFSG，或因专利等法律问题使分发存在问题；须满足"它们能满足的"policy 要求。
- （另：non-free-firmware 为固件特设，允许进入官方安装镜像）

**谁执行**：Debian Policy + ftp-master 归档审核。

**强制/自律**：**强制分区**（硬性归档规则）。

**教训**：
- ✅ **分区的判据是"许可证与依赖的自洽性"，不是"软件好坏"**。这与 Android 一样，是"**分什么**"的又一次范式纠正：分的是**属性**（能不能自由再分发、依赖干不干净），不是**评分**。
- ✅ **"依赖不外溢"这条极有移植价值**：main 不依赖区外的规则，等价于 DSH 第一级可以规定"不得依赖未声明的外部运行时 / 不得依赖开发者自己的私有服务"。这是**可机器判定**的。
- ✅ Ubuntu 的 supported/universe 分的是**维护承诺**（谁负责安全更新），而非质量——Canonical 官方维护 vs 社区维护。**"谁负责"比"有多好"更容易分级，也更容易验证**。这条对 DSH 的启示：第三级可以定义为"有人署名承诺维护并给出响应时限"，而不是"代码更优秀"。

## 2.3 跨生态归纳：七条共性规律

1. **能长期存活的分级，判据都是"属性"而非"质量"**：许可证（Debian）、权限等级（Android）、身份（MCP 命名空间）、元数据自洽（Koishi、VS Code）、维护承诺（Ubuntu）。**凡是做"质量打分"的（npm score、市场五维评分），都出现了失真与被博弈。**
2. **准入制必须与"不合格者的去处"配套**：Homebrew 的第三方 tap、Debian 的 contrib/non-free。没有出口的门槛要么形同虚设，要么扼杀长尾。
3. **审核是快照，攻击是慢变量**：Chrome 的 108 扩展案是分水岭证据。任何一次性结论都必须配**周期性复审 + 版本锚定**。
4. **发布主体与执行主体分离**：MCP Registry 的元注册中心分层（规范中立 / 徽章下放）是对 Apple 模式（标准+评审+上诉+分销四合一）的直接反动。
5. **强制力必须落在代码上**：Android 靠框架运行时执行、Koishi 靠市场索引、VS Code 靠 `vsce`、Debian 靠归档规则。**没有执行落点的"强制级"只是徽章**。
6. **必须预先声明"这不是安全背书"**：Chrome、Homebrew、MCP 都有明文。dshbase 的"Verified = CI 跑通 `dsh plugin add`，仅此而已"也是这个范式。
7. **知名度门槛与长尾保护直接冲突**：Homebrew 75★ 门槛在 DSH 生态会砍掉 590 条 6–10★ 条目。**DSH 第一级应零知名度门槛。**

## 3.2 逐项判定：能否承载"标准符合性"

**判定标准**（四条，缺一不可）：① 判据公开且可复核；② 结果可判定（是/否或三值，非连续分）；③ 有版本锚与不可变证据；④ 有被生态承认的发布主体 + 执行落点。

| 项目 | ① 判据公开 | ② 可判定 | ③ 版本锚/证据 | ④ 主体+执行 | **能否承载** |
|---|---|---|---|---|---|
| dsh-plugin-doctor | ✅ 分组与 exit code 契约公开 | ✅ **三值 PASS/WARN/FAIL + 0/1/2** | ✅ `--dsh` 宿主版本 + coverage + 防假绿 | ❌ 无权威主体、无执行落点 | **能承载"检测"，不能承载"判定"**。它是**最接近 DS-C 门禁的存在**——只差一条"由谁宣布它算数" |
| dsh-score | ✅ 五维权重公开 | ❌ **连续加权分** | ⚠️ 评的是 repo/npm 包，**不是 commit**；有 `observedAt` | ❌ | **不能**。`compliance` 只占 15 分且被加权稀释——一个合规不及格的插件可靠文档/热度把总分拉高，这正是"评分即排名"扭曲的入口。可作 DS-R 的**参考输入**，不可作判定 |
| 2BingLing/dsh-market | ⚠️ 维度公开、权重部分公开 | ❌ 连续分（几何平均） | ❌ 无 commit 锚 | ❌ | **不能**。定位是发现与推荐。它的"安全模式"（安装前扫描、有问题即中止）反而是**一个真正的执行落点**，值得被三级标准吸收 |
| dsh-plugin-hub | ⚠️ 检查项未形成**可分叉的规范文本** | ✅ verified/unconfirmed | ✅✅ **不可变护照 + commit + 扫描器版本**（生态唯一） | ⚠️ 有站点，但"岚叔严选"= 单点人审 | **能承载"证据层"，不能承载"条款层"**。这是三级标准的**证据基础设施最佳宿主**；需把它的检查项反向沉淀为公开条款，并把"严选"从个人决策变成可轮换的工作组决策 |
| awesome-dsh-plugin | ✅ contributing.md | ✅ 收录是二值的 | ❌ 无版本锚 | ⚠️ 有社区承认度，但**"一个 PR 最多 3 条 + 人工读源码"** | **能承载"准入下限"（≈ DS-C 的地板），且主动拒绝承载分级**。其人工核对模式在 2,686 个 >5★ 仓库 / 7,723 条快照面前**不可扩展**——是"评审者成为瓶颈"的现成例证 |
| dsh-plugin-catalog | ✅ format-1 | ❌ 无评级语义 | ❌ | ❌ | **不能，但应作为承载格式**。把等级字段写进索引（或扩展 format-2）是最省力的分发路径 |
| 🧊FROZEN / 🚫RETIRED | ⚠️ 语义靠 README 自述 | ⚠️ 二值但无枚举 | ❌ | ❌ | **不能单独承载，但必须被吸收**。三级体系需要机器可读的 `status` 枚举（active / frozen / retired / unknown），这正是它缺的 |

## 3.3 结论：现状是"六块积木 + 三个缺口"

现有尝试已经铺好了六块积木：**检测**（doctor）、**打分**（score / market）、**证据**（hub 护照）、**准入**（awesome）、**格式**（catalog）、**退出**（FROZEN/RETIRED）。

但**没有一块能承载"标准符合性"**，缺的是三样东西：

1. **主体缺口**：所有项目的发布者都是个人或小团队（PerryLink / 2BingLing / 岚叔 / awesome 维护者）。**没有任何一个主体拥有"宣布某插件符合某级"的生态授权**。这正是 GB 与 GB/T 之间那条"国务院批准"鸿沟的 DSH 版本。
2. **规则缺口**：doctor 已经有漂亮的三值输出，但**"三值 → 等级"的映射规则不存在**。R 组 FAIL 是掉一级还是直接不合格？K 组 WARN 容忍几条？这类规则没有公开文本，因此无法被分叉、被质疑、被改进。
3. **执行缺口**：没有任何东西让"不符合"产生后果——装还是能装、收还是照收。**没有执行落点的等级，等价于一个 README 徽章**。

**因此，三级标准的正确姿势不是另起炉灶，而是给已有积木补上这三样**：
- 把 **doctor 的 R/K/D** 映射为 **DS-C（第一级）** 的条款；
- 把 **hub 的护照机制** 作为统一的**证据层**；
- 把 **catalog（format-1 或其扩展）** 作为**分发层**；
- 把 **awesome 的准入四问** 作为 **DS-C 的地板**（且它自己已经写明了"不排名"）；
- 把 **FROZEN/RETIRED** 升级为**机器可读的 `status` 枚举**，作为**日落机制**；
- 把 **market 的安全模式** 作为**唯一真正的执行落点**（安装前中止）。

# 四、治理教训与治理原则

## 4.1 四类已被证实的副作用（附实证）

### 副作用 1：评分即排名 → 刷分与指标扭曲（Goodhart 定律）

**实证**：
- Zahan et al.（ICSE-SEIP 2023，2,422 个 npm/PyPI 包）：安全实践总分与已报告漏洞数呈**反直觉的正相关**——高分不等于更安全。
- OpenSSF Scorecard 自陈："The checks themselves are heuristics; there are false positives and false negatives."；公开检查项 + 公开分数 ⇒ "a motivated project can optimize for the score without improving real security posture"。
- DSH 内已有苗头：dsh-score 的 `compliance` 权重仅 15/100，被其他四维稀释；2BingLing/dsh-market 的"生态热度"维度直接把流行度计入推荐度。两者都存在"靠非质量维度把总分抬上去"的通道。

**推论**：**DSH 三级标准必须输出"符合 / 不符合 / 部分符合"的三值，不得输出总分，不得生成排行榜。** 一旦有排行榜，就会出现为排行榜优化的插件（README 灌水、无意义 commit 续命、互刷 star）。

### 副作用 2：门槛过高 → 扼杀长尾

**实证**：
- Homebrew 知名度门槛 30 forks / 75 stars（自荐 90/90/225）+ 仓库 ≥30 天，在 DSH 生态会**几乎全数排除 6–10★ 区间的 590 条**（dsh-market 快照口径），而这一层恰恰是 DSH 当前最活跃的单功能插件带。
- VS Code / Chrome 的门槛（格式、manifest）之所以合理，是因为它们**只卡格式不卡质量**。
- Chrome 案的另一面：攻击者靠 108 个长尾货位撞长尾搜索命中率——**长尾既是生态活力所在，也是攻击面所在**。所以正确做法不是抬高门槛砍掉长尾，而是**给长尾打上可判定的标签**（权限面、维护状态、证据有无），让使用者自己筛。

### 副作用 3：评审者成为瓶颈与权力中心

**实证**：
- Apple：唯一分发渠道 + 唯一评审者 + 唯一上诉法院；"同一功能这次过、下次拒"；评审竞品应用时可接触竞争对手商业敏感数据（英国 CMA 2025 SMS 调查原文列举）。
- DSH 内已现端倪：awesome-dsh-plugin 的"一个 PR 最多 3 条 + 维护者人工读源码"，在 2,686 个 >5★ 仓库面前**结构性不可扩展**；dsh-plugin-hub 的"岚叔严选"是**单人署名决策**。
- 两个项目都还是健康的，因为规模尚小。**一旦"标准符合性"与"市场排名/收录"挂钩，这两个位置会立刻变成权力位。**

**推论**：强制级必须**由机器执行**（消除瓶颈），推荐级由**可轮换的工作组共识**，指导级**允许个人署名发布**（仿 GB/Z 登记制）。**绝不允许单个人拥有跨三级的否决权。**

### 副作用 4：标准僵化 → 跟不上宿主迭代

**这是 DSH 特有的、且最严重的一条。** 本地核验：
- `README.md:13`："DeepSeek Harness is in _developer preview_ and iterating rapidly. **THERE WILL BE COMPATIBILITY-BREAKING CHANGES.**"
- 仓库 `package.json` version = `0.2.2-alpha.2`（npm 主线另在 `0.2.1-rc.x`）
- `vendor/cordis/package.json` = `@deepseek-ai/cordis@4.0.6-alpha.1` —— **注意：是 alpha，比"rc"更不稳定**

**推论**：
- 任何写入标准的 Cordis API 细节都有**极短保质期**。标准必须**与宿主版本号共同版本化**（`标准版本 × dsh 版本 × cordis 版本` 三元组）。
- 第三级（充分利用 Cordis 特性）是**最短命的一层**，必须配最短的复审周期——这正是 GB/Z 的制度答案：**规范类指导性技术文件复审周期最长不超过 3 年，结论可以是"废止""继续有效（继续使用期限一般不超过 3 年）""制定为推荐性国家标准"**。DSH 的迭代速度以周计，建议**第三级复审周期压到 3 个月**，并**默认允许"直接作废"**。
- 反面：如果三级标准把第一级写成"必须调用 Cordis 的某某 API"，宿主一次 minor 升级就会让全生态集体不合规——**标准会把生态锁死在一个 alpha 版本上**。因此第一级的条款应尽可能写成"**不依赖具体 API 的**"（装得上、起得来、声明了权限面、卸载干净）。

## 4.2 八条治理原则

> 原则编号 G1–G8。**前四条是设计约束（写标准时必须遵守），后四条是运营约束（跑起来之后必须遵守）。**

**G1 · 可判定优先于可评价**
每一级每一条必须是**机器可判定**的，输出三值（PASS / WARN / FAIL），禁止主观项（"文档写得好不好""设计是否优雅"）进入第一级。直接复用 `dsh-plugin-doctor` 已有的 exit code 契约与 `--format check` 三值视图。**不可判定的条款一律下沉到第三级（指导级）或干脆不写。**

**G2 · 分级不排名**
等级是"符合条款的集合"，**不是分数**。禁止把三级折算为总分或排行榜；对外只展示徽章 + 证据页链接 + 复核日期。awesome-dsh-plugin 已经给出了正确示范："We don't rank plugins or judge their quality, and we don't want to."

**G3 · 版本锚 + 不可变证据**
任何符合性声明必须绑定五元组：**(repo, commit, scanner 版本, dsh 版本, cordis 版本)**。直接采用 `dsh-plugin-hub` 的"插件护照"机制（不可变证据页 + 原始 JSON + 检查文件清单）。理由：Chrome 案的教训是"审核是快照，攻击是慢变量"——**没有 commit 锚的等级，等于对一个会漂移的目标发证书。**

**G4 · 三值 + 覆盖度披露，禁止假绿**
必须显式记录"哪些检查真跑了、哪些被跳过"。`dsh-plugin-doctor` 已经踩过这个坑并在 0.2.0 修掉：无 `src/` 也无 `lib/` 时 9 条 K 检查全部 skip 却仍 exit 0（**假绿**），现改为 exit 6 + `coverage.K` 披露。**降级通过必须显式声明（`--allow-degraded`），默认拒绝。**

**G5 · 复审周期与层级稳定性成反比**
- 第一级（DS-C）：跟随宿主 minor 版本复审，目标是最稳定
- 第二级（DS-R）：跟随宿主 minor 复审，周期不超 6 个月
- 第三级（DS-G）：**复审周期 3 个月**，到期结论三选一 —— 废止 / 继续有效 / **升为 DS-R**
- 仿 GB/Z 第二十六条的"废止 / 继续有效 / 制定为推荐性国家标准"三结论，这是 GB/Z 制度里**最值得借的机制**。

**G6 · 日落与上诉对称**
必须有退出通道（把 🧊FROZEN / 🚫RETIRED 升级为机器可读 `status` 枚举：active / frozen / retired / unknown），也必须有**可申诉的复核通道**与**分层上诉**（Apple 的教训：无制衡的单点评审者是最糟的形态）。下架/撤销需满足 Homebrew 式的**证据标准**：精确定位文件+版本+校验和+多来源，VirusTotal 单独不足为凭。

**G7 · 执行者分层且可轮换，杜绝单点评审者**
- 第一级：**工具自动执行**（消除瓶颈）
- 第二级：**生态工作组共识**（成员轮换、决策留痕、可 fork）
- 第三级：**个人/小团队署名发布**（仿 GB/Z 登记制：登记即启动，1/2 赞成即通过，12 个月上限）
- 仿 MCP Registry 的元注册中心分层：**条款中立、徽章下放**。任何组织不得同时"写标准 + 发徽章 + 运营唯一市场"——那是 Apple。

**G8 · 不冒充官方、明示免责、门槛不设知名度**
- 任何徽章必须写明"非官方、非安全审计、非背书"+"复核日期"。`dsh-plugin.org` 的"我们只是社区项目，与 DeepSeek AI 没有隶属关系""链回官方，不冒充官方"是正确的治理姿态；`dshbase` 的"Verified 仅表示 CI 跑通 `dsh plugin add`"也是。
- **第一级零知名度门槛**（不设 stars/forks 下限），否则会砍掉 DSH 生态 590 条 6–10★ 长尾。质量靠 G2 的证据页让使用者自己筛，**不靠门槛替使用者筛**。
- 仿 Homebrew：**不合格者必须有去处**（第三方目录 / 未分级展示），这是门槛能维持的前提。

# 五、命名建议

## 5.1 直接借用 GB / GB-T / GB-Z 的风险

### 法律层面

1. **"GB"是国家标准专属代号，有明确的规章依据**。《国家标准管理办法》第三十二条："强制性国家标准的代号为'GB'，推荐性国家标准的代号为'GB/T'……指导性技术文件的代号为'GB/Z'。"标准化法第二十四条："标准的编号规则由国务院标准化行政主管部门制定并公布。"
2. **社会团体/企业自定标准有法定编号体系，且违规可被处罚**。标准化法第四十二条："社会团体、企业未依照本法规定对团体标准或者企业标准进行编号的，由标准化行政主管部门责令限期改正；逾期不改正的，由省级以上人民政府标准化行政主管部门**撤销相关标准编号，并在标准信息公共服务平台上公示**。"（团体标准的法定前缀是 `T/`，企业标准是 `Q/`）——**民间标准有合法通道，只是它的前缀不是 GB。**
3. **冒用/混淆国家标准名义已被实际执法**。2026 年市场监管总局的团体标准乱象专项整顿（"绵羊绒"案：中国畜产品流通协会的团体标准被责令废止）；2025-08-22 市场监管总局认证监管司点名"医护级""特护级""领先""超级""先进"等认证字样，理由是**把自愿性/团体级认证包装成看似国家等级、混淆标准等级、误导消费者**。DSH 若用"GB / GB/T / GB-Z"给插件分级，属于同一类**认知混淆风险**：把社区自律文件包装成看似有国家强制力背书的等级。
4. 尽管在开源社区内部使用未必会立即触发执法，但 DSH 生态**已经有商业化市场、收费目录与"严选"推荐**（dsh-market / dsh-plugin-hub / 各类 1024 Store），一旦等级与商业推荐挂钩，"借用国家代号 + 商业背书"的组合风险显著上升。

### 认知层面（比法律更早发生）

1. **GB 自带"国家强制力"联想**。中文语境里"符合 GB"≈"合法、必须、有国家背书"。而 DSH 生态里**唯一有强制力的是宿主运行时**，社区组织一律没有。**借 GB 会同时高估承诺（使用者以为官方认证）并低估现实（DSH 还在 developer preview）。**
2. **GB/GB/T/GB/Z 的真实差别是"法律效力来源"，DSH 三级之间是"可判定性与稳定性"的差别**——**维度不同**。借用会掩盖真正的设计变量（权限面、契约正确性、稳定性），把注意力引向"级别高低"。
3. **第三级会被系统性误读**。见 §1.4：GB/Z 恰恰是"技术尚在发展中、尚不具备制定国家标准条件"时的引导性文件，**它比 GB/T 更不成熟，不是更高级**。若沿用该结构却又把第三级叫"高级/进阶"，就同时犯了两个错：既误读 GB/Z，又诱导作者追 alpha API。

### 生态与品牌层面

1. DSH 是**国际开源项目**（`deepseek-ai/deepseek-harness`，仓库内 `README.i18n.yaml` / `BRAND_GUIDELINES.md` / `BRAND_GUIDELINES.i18n.yaml` 齐备，多语言并行维护）。用一国标准体系的代号给全球生态分级，**非中文用户完全无法解码**——"GB-T"对英文读者是三个无意义字母。
2. 仓库已存在 `BRAND_GUIDELINES.md`，说明官方对品牌与命名的一致性有明确治理意图。生态侧自造一套与国家代号同形的命名，与该取向冲突。

## 5.2 候选命名对比

| 方案 | 三分结构 | 优点 | 缺点 | 判定 |
|---|---|---|---|---|
| **GB / GB-T / GB-Z** | 强制 / 推荐 / 指导 | 中文用户秒懂；结构现成 | 法律风险（国家代号专属）、认知混淆（假强制力）、国际不可解码、第三级语义易反转 | ❌ **不推荐** |
| **DS-S / DS-T / DS-G** | S(标准/强制) / T(推荐) / G(指导) | 与 GB/GB-T/GB-Z 一一对应，内部迁移成本低；不含国家代号 | `DS-T` 与 `GB/T` 形近，仍有认知混淆余温；**S/T 语义不自明**（非中文读者无法解 T=推荐）；S 与 "Standard" 冲突（三级都是 standard） | ⚠️ 可用但不优 |
| **DS-C / DS-R / DS-G** | **C**ore / **R**ecommended / **G**uidance | 三个字母在英文中语义自明、可国际传播；与 GB/GB-T/GB-Z **结构一一对应**；不含任何国家代号；`DS` 前缀明确归 DSH，避免与 VS Code/Chrome/Koishi 的既有等级混淆 | 需要一段"与 GB 三分法同构"的说明文字（这个成本很低） | ✅ **推荐（主方案）** |
| **Core / Recommended / Advanced** | 核心 / 推荐 / 高级 | 最直白 | **"Advanced" 是语义反转**（见 §1.4）；"Core" 易被读成"核心插件/官方内置"，与"只是基线门槛"的原义冲突；无生态前缀，跨生态撞名 | ❌ 不推荐（若用，须改 Advanced → Guidance/Frontier） |
| **L1 / L2 / L3** | 三级 | 极简、中立、不承诺语义 | **级别数字天然暗示"越高越好"**，会激起刷级；丢失"强制/推荐/指导"的性质差异（这正是三分法的精髓） | ⚠️ 只适合做内部代号，不适合对外 |

## 5.3 推荐方案

### 主推荐：**DS-C / DS-R / DS-G**

| 代号 | 全称 | 中文 | 国标对应 | 语义 | 强制力 |
|---|---|---|---|---|---|
| **DS-C** | **C**ore | **基线级** | GB | 装得上、起得来、权限面可声明、卸载干净。**不满足即不应被任何主流市场默认收录** | 由工具执行 + 市场前置门禁（对应 GB 的"不符合不得提供"） |
| **DS-R** | **R**ecommended | **推荐级** | GB/T | 与 Cordis 契约正确对齐：生命周期、服务依赖声明、配置 schema、错误处理 | 鼓励采用；下游市场/企业 policy 可声明"只采用 DS-R 及以上"，此时在该范围内产生约束力（对应 GB/T 的"纳入合同即具约束力"） |
| **DS-G** | **G**uidance | **指导级** | GB/Z | 充分利用 Cordis 特性的高阶用法与最佳实践。**技术仍在发展中，不保证稳定** | **参考使用，无强制**；个人署名发布、登记制、**3 个月复审**、可废止可升为 DS-R |

**配套三个强制约束：**
1. **徽章与文档中禁止出现 "GB" 字样**，禁止把三级简称为"国标"。
2. **可以做类比说明，但不得做命名借用**。允许在规范开头写一句："本规范的三分结构参照 GB / GB-T / GB-Z 的'强制 / 推荐 / 指导'三分法设计，但**与国家标准体系无任何隶属或等同关系**，代号不借用。"——**借机制、借结构，不借名字。**
3. **每一级徽章必须同时显示：等级 + commit 锚 + 复核日期 + "非官方、非安全审计"免责**。

### 一个容易被忽略的命名细节：**状态位与等级位要分开**

等级（DS-C/R/G）回答"**符合什么**"；状态（借鉴 🧊FROZEN / 🚫RETIRED）回答"**还活着吗**"。二者必须分开建模，且状态要**机器可读**：

```
status: active | frozen | retired | unknown
level:  DS-C | DS-R | DS-G | ungraded
```

理由：dsh-plugin.org 需要专门写教程教用户分辨 stalled / archived / frozen，说明**仅靠 README 自述的状态是不可靠的**；而"frozen 但仍是 DS-R"与"active 但是 ungraded"是两种完全不同的风险，混在一起会毁掉等级的信息量。
